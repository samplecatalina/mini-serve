# Optimization log

Each entry records what was expected before a change was measured, what was measured, and why the two differ. Performance numbers link to rows under `results/` or reports under `profiling/`; correctness findings link to tests.

## M0 — Environment, reference model, correctness anchor

M0 has no performance changes. The entries below are the findings that shaped the test infrastructure every later change is judged by.

| Hypothesis | Prediction | Measured | Difference | Evidence |
|---|---|---|---|---|

## M1 — Continuous batching, paged KV cache, sampling, API

M1 has no performance measurements: its changes are judged by the correctness anchor and by stress tests, not by throughput. The tolerance policy used from here on: a batched or paged path may diverge from the reference only at a position where the reference's top-2 logit gap is at most ε = 0.5, and, fed its own output, the reference must rank each chosen token within ε of its maximum ("teacher-forced margin").

| Hypothesis | Prediction | Measured | Difference | Evidence |
|---|---|---|---|---|
| Running requests together (token-flattened batch, per-request contiguous KV) leaves greedy output unchanged except at near-ties. | Divergence from single-request output is rare and happens only where the top two logits are nearly equal. | Single-request path: 6/6 prompts token-identical to the reference. Concurrent: 5/6 (all at once) and 6/6 (staggered) sequences diverge within 128 tokens; at every divergence the reference top-2 gap is 0.0 or 0.125; teacher-forced margin at most 0.1875. A 32-request probe diverged on 42/64 sequences, 27 of them at exact BF16 ties. | Divergence is common, not rare: 2.1% of reference positions are exact ties, so a 128-token sequence very likely meets one, and any 1-ulp perturbation flips a tie. The margin near the top never exceeded 0.25. First-divergence checking alone missed an injected batching bug that the teacher-forced margin caught, so both checks are part of the anchor. | `tests/test_engine.py` (`test_concurrent_matches_reference`) |
| A reference-counted block allocator has no external fragmentation. | After any interleaving of allocations and frees, all free blocks can be allocated at once; internal waste per request is below one block. | Unit and randomized tests pass; 10/10 injected allocator bugs detected; forward-path results unchanged. | None. | `tests/test_block_allocator.py` |
| FlashInfer paged attention over 16-token blocks passes the same anchor as the contiguous path. | Even single-request output is no longer bitwise (a different kernel), but divergences stay within ε = 0.5. | Batch-1 decode logits differ from the reference by up to 0.68; 5/6 single-request prompts diverge, all at ties. A 32-request probe: 50/64 divergences, largest top-2 gap at a divergence 0.125, teacher-forced margin at most 0.25. Non-contiguous and descending block layouts pass. | As predicted for the kernel. Unexpected: shifting every decode position by one passed both token-level checks, because RoPE only sees relative positions and a uniform shift looks like an empty slot between prompt and output. An exact assertion on the positions fed to the model at every step now covers it. | `test_single_request_paged`, `test_paged_fragmented_pool`, `test_positions_contract` |
| Admission against a KV block budget with recompute preemption neither deadlocks nor changes output. | 64 mixed requests in a pool of at most 2048 tokens finish with preemptions, no out-of-memory error, and anchor-conforming output. | All at once, 2048-token pool: 234 steps, 11 preemptions, 13/64 divergences, gap ≤ 0.125, margin ≤ 0.1875. Staggered arrivals, 1536-token pool: 275 steps, 32 preemptions, 15/64 divergences, gap ≤ 0.125, margin ≤ 0.25. Positions exact at every step, including recomputed prefills; all blocks returned. A CPU simulation (30 randomized runs, 4–35 preemptions each) matches running each request alone token for token. | Preemption with recomputation adds no new numerical behaviour. Unexpected: preemption count is not monotonic in pool size (768 / 1024 / 1536 / 2048 tokens → 36 / 0 / 32 / 10) because long requests (~580 tokens) pack into the pool differently at each size. | `test_concurrent_matches_reference`, `test_simulated_load_under_kv_pressure`, `miniserve/tools/stress.py` |
| Sampling can run entirely on the device with one readback per step, and greedy rows are unaffected by sampled neighbours. | No host synchronization in the sampler; greedy rows equal `argmax`; sampled rows follow `softmax(logits / T)` restricted to the nucleus. | The sampler runs under CUDA sync-debug mode "error"; greedy rows equal `argmax` including ties and mixed batches; 50,000-draw frequencies match the target distribution within 0.01 and tokens outside the nucleus never appear; a request samples the same tokens at any row of any batch and after preemption. | FlashInfer's sampling kernels draw random numbers by row position (a request's sample depends on its neighbours), so sampling uses Gumbel-max with noise hashed from (request seed, token position, vocabulary index). Unexpected cost: the `[64, vocab]` temporaries peak at 510 MB, more than the activations of an 8192-token prefill, and the auto-sized KV pool shrank from 2772 to 2631 blocks. | `tests/test_sampler.py` |
| An engine thread behind a command queue, with an HTTP front end, serves streaming requests without changing output and without leaking KV blocks on cancellation. | Greedy text over HTTP equals offline output; cancelled requests return all blocks whether queued, decoding or requeued after preemption. | Greedy text over HTTP equals the offline text of the same request on the same engine. 32 concurrent HTTP requests in a 1536-token pool, 15 disconnected at random points: 21 preemptions, aborts reached the engine in both waiting and decoding states, and all blocks were free once idle. Streamed increments concatenate to the full decode and never contain half a character. | A test that only checks "all blocks free once idle" cannot show that cancellation works: a request that is never aborted also finishes and frees its blocks within the wait. The end-to-end test therefore also asserts that aborts reach the engine; an injected "disconnect never aborts" bug was caught only by that assertion. | `tests/test_server.py` |

## M2 — Prefix cache and chunked prefill

Measured on an RTX 4060 Laptop GPU with the engine-level harness (`bench/offline.py`: open-loop arrivals straight into the engine, settings alternated in one process, median of 3 runs per setting). Each prediction below was committed before the measurement it predicts. The share-of-peak figure is left out until this repository measures its own peak bandwidth and GEMM throughput.

| Hypothesis | Prediction | Measured | Difference | Evidence |
|---|---|---|---|---|
| Requests that share a long prompt prefix skip most of their prefill with a block-granular radix cache, and fit in the KV pool together. 64 requests in 8 groups sharing 1024-token prefixes (+64 own tokens, 64 output), all arriving at once, 32k-token pool. | Hit rate 0.75; prefill tokens 17,408 vs 71,844 (-76%); mean decode batch 64 vs 21; output throughput +114% (range +60% to +150%); TTFT p50 -80%. | Hit rate 0.75; prefill tokens 17,408 vs 71,844; decode batch 64.0 vs 21.3; **1487 vs 409 tok/s (+263%)**; TTFT p50 1239 vs 4630 ms (-73%); ITL p99 28 vs 633 ms. | Throughput far above the predicted range. The model charged decode for reading every sequence's KV from DRAM; in fact the attention kernel reads a shared block from DRAM once and serves the other sequences from L2, so a decode step over 64 requests costs about what one over 21 does (~29 ms per step either way under the profiler). The unshared baseline was predicted within 3%. | `results/rtx4060-laptop/m2_1_radix.csv`; `profiling/rtx4060-laptop/m2_1_radix_shared_burst.nsys-rep` |
| Decode attention over shared KV blocks moves only the distinct bytes through DRAM. One layer, 64 sequences of 1152 tokens (288 MiB of logical KV). | DRAM traffic falls toward the distinct KV when blocks are shared. | All distinct: 302.4 MB read from DRAM, L2 hit rate 0.15%. 8 groups sharing 1024-token prefixes: 67.4 MB (distinct KV: 64 MiB = 67.1 MB), L2 hit rate 77.7%. All sharing one prefix: 38.0 MB (distinct 36 MiB), 87.4%. | As hypothesized after the throughput surprise above. Kernel timings of this microbenchmark are not used: its all-distinct case ran into a software power cap at a lower clock. | `profiling/rtx4060-laptop/m2_1_decode_sharing_*.ncu-rep`; `results/rtx4060-laptop/m2_1_decode_sharing.csv` |
| With Poisson arrivals (4 req/s) the same workload gains in TTFT, not throughput; without sharing, the prefix cache costs nothing measurable. | Shared: hit rate 0.81, TTFT p50 -64% (range -40% to -75%), throughput unchanged. Unshared: within 3%. | Shared: hit rate 0.82, TTFT p50 31.0 vs 74.4 ms (-58%), throughput +0.2%. Unshared: within 1% (TTFT p95 -3.7%, the run-to-run spread of that percentile). | As predicted. | `results/rtx4060-laptop/m2_1_radix.csv` |
| Batching prefill chunks with decodes (decode first, per-step token budget) cuts the inter-token latency tail that whole prefills cause. 64 requests at 4 req/s, 8 of them 3072-token prompts (16 output), the rest 256-token prompts (128 output). | ITL p99: 512-token chunks -27%; **2048-token chunks +112%** (a stall spread over more steps pushes more gaps above the 99th percentile); ITL max -68% / -89%; long-prompt TTFT +18% / +61%; throughput unchanged. | ITL p99 44.9 (512) / 122.5 (2048) vs 60.9 ms unchunked (-26% / +101%); ITL max 48 / 143 vs 466 ms; long-prompt TTFT p50 285 / 224 vs 217 ms (+31% / +3%); throughput unchanged. | The ITL predictions held, including the worse tail with large chunks. Long prompts were slowed less than predicted because a chunk costs less inside a mixed step than the model assumed (next row). | `results/rtx4060-laptop/m2_2_chunked.csv` |
| Chunking costs some throughput when many prompts arrive at once (64 × 1088 tokens). | ITL p99 -74% (2048) / -90% (512); throughput unchanged to -10%. | ITL p99 129 / 47 vs 615 ms (-79% / -92%); **throughput 484 / 535 vs 420 tok/s (+15% / +27%)**; ITL p50 28.5 / 45.7 vs 28.3 ms. | Throughput went the other way. Decode-only steps leave the GPU 52–65% busy (CPU-side work per step); a mixed step with a 512-token chunk is 89% busy and takes ~44 ms against ~29 ms for a decode-only step, so its ~480 prefill tokens cost ~0.03 ms each against ~0.07 ms in prefill-only steps. The cost of small chunks shows in the median ITL instead (+62%). This effect should shrink once decode steps stop being CPU-bound. | `results/rtx4060-laptop/m2_2_chunked.csv`; `profiling/rtx4060-laptop/m2_2_chunked_unique_burst.nsys-rep` |

Correctness for both changes: all anchor tests pass with the prefix cache and chunked prefill enabled; a 563-token prompt prefilled in 64- or 100-token chunks gives last-position logits within 0.23 of one whole prefill on the reference path; concurrent, chunked and preempted runs pass the tolerance policy with exact positions at every step. With a prefix cache, a request's greedy output can differ at BF16 near-ties depending on what is cached, so exact comparisons start from an empty cache.

## M3 — CUDA Graphs, overlap scheduling, scheduling policies

Same harness and conventions as M2 (median of 3 runs per setting, settings alternated in one process, each prediction committed before its measurement; share of peak left out).

| Hypothesis | Prediction | Measured | Difference | Evidence |
|---|---|---|---|---|
| Replaying each decode step from a CUDA Graph removes the per-kernel launch cost of an eager step (hundreds of kernels issued from Python), which dominates small batches. | 4 requests at once: ITL p50 -25%, throughput +30%. 4 req/s stream (decode batches of about 8): ITL p50 -27%. 64 requests at once: within 3%, on the assumption that eager decode there is already GPU-bound. | 4 requests: ITL p50 10.1 vs 19.6 ms (**-48%**), 362 vs 194 tok/s (**+87%**). 4 req/s: decode step 8.45 vs 19.77 ms, ITL p50 8.6 vs 19.8 ms (-56%), ITL p99 30 vs 124 ms. 64 requests: 538 vs 475 tok/s (**+13%**). | Right direction, half the size. The prediction took the GPU time of an eager step with all its kernels queued in advance as the floor a graph can reach; a graph replay beat that floor, so kernels issued one by one cost GPU time as well as CPU time on this platform. In the 64-request burst the timeline shows the same GPU work per decode step either way (about 19 ms) with the GPU 61% busy in an eager step and 96% in a graph step: eager decode was not GPU-bound. | `results/rtx4060-laptop/m3_1_cuda_graph.csv`; `profiling/rtx4060-laptop/m3_1_cuda_graph_unique_burst.nsys-rep` |
| Chunked prefill raised burst throughput (M2) by filling GPU time that eager decode steps left idle, so with graphs the gain should shrink. | Stays near the eager +27% (the prediction, from the eager-floor measurement above, doubted that idle time existed). | 512-token chunks vs none, with graphs: 556 vs 460 tok/s (+21%). | The gain shrank by about 6 points, so idle-filling was part of it; the rest comes from mixed steps themselves (one forward pass for decode rows and a chunk instead of two). Cross-commit comparison, supporting evidence only. | `results/rtx4060-laptop/m3_1_chunked_under_graph.csv` |
| Overlap scheduling (launch step t+1 before reading back step t) hides the CPU part of each step; with decode graphs little CPU time is left to hide. | With graphs: 64 requests +2 to +5%, 4 requests +3%, 4 req/s ITL p50 -2 to -4%. Without graphs: +4 to +6%, bounded because an eager decode step is CPU-bound and overlap cannot make a step shorter than its CPU time. GPU busy fraction toward 99%. | With graphs: 64 requests 543 vs 528 tok/s (+2.9%), 4 requests +1.6%, 4 req/s ITL p50 8.55 vs 8.73 ms (-2.1%), ITL p99 -6.9%. Without graphs: 203 vs 190 tok/s (+7.2%). Over the 64-request run the GPU was idle 155 vs 344 ms (97.9% vs 95.6% busy). **TTFT p50 +4% (4 requests) and +26% (4 req/s, 38.8 vs 30.8 ms).** | Within or near the predicted ranges: a small result, as expected once decode is replayed from graphs. Not predicted: time to first token gets worse, since a sampled token is read back one step later, after the next step is launched; that costs about one decode step, which is large next to the 31 ms TTFT of short prompts. | `results/rtx4060-laptop/m3_2_overlap.csv`, `m3_2_overlap_eager.csv`; `profiling/rtx4060-laptop/m3_2_overlap_unique_burst.nsys-rep` |
| Admission order matters only while requests queue for KV. 128 requests at once in 16 groups sharing 512-token prefixes (32 own tokens), 25% asking for 512 output tokens and the rest for 32. | Pools of 6k / 8k tokens: cache-aware throughput +16% / +17%, mean latency -15%; shortest-job-first mean latency -49% / -42%, short requests -80% / -74%, long-request p99 +1% / -5% (a single burst does not starve long requests). 16k tokens: all within 5%. Cache-aware might gain more than predicted, as the model ignores cheaper decode over shared blocks. | 6k / 8k: cache-aware **+25% / +27%** throughput (947 / 1136 vs 758 / 894 tok/s), mean latency -25% / -24%, hit rate 0.79 / 0.78 vs 0.44 / 0.52; shortest-job-first mean latency **-49% / -42%**, short requests -80% / -74%, long-request p99 +2% / -4%, throughput -4% / +4%. 16k: throughput and latency within 5%, except cache-aware's ITL p99, 91 vs 32 ms. | Shortest-job-first matched the prediction closely. Cache-aware gained about 10 points more, in the direction noted beforehand. The ITL tail of cache-aware in the large pool was not predicted; it is repeatable (91 ms in all three runs) and sits at the length of a mixed step, which suggests that its admission pattern puts more decode gaps behind long mixed steps (unverified). | `results/rtx4060-laptop/m3_3_policy.csv`; `profiling/rtx4060-laptop/m3_3_policy_pool8192.nsys-rep` |

Correctness: every anchor test passes with graphs, overlap and each policy (the default settings run graphs and overlap, so the whole suite exercises them; concurrent anchors also run with each switched off). A decode graph's logits equal an eager step's bit for bit when no padding changes the batch shape, and stay within the tolerance when it does; padding rows write only a spare block, checked byte for byte over the whole pool. A test that queues a long sleep kernel between steps checks that launching a step never waits for the device; it found two blocking copies on the launch path, both fixed. Measuring the policies found a bug in the graph path: with a prefix cache, a batch's page indices can outnumber the pool's blocks, which overflowed a buffer sized to the pool; it is fixed and covered by a test, and earlier measurements did not share blocks across requests in decode.
