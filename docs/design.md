# mini-serve — Design

A single-GPU LLM inference engine built as a reproduction, with additions, of
[mini-sglang](https://github.com/sgl-project/mini-sglang). The features that
mini-sglang already ships (overlap scheduling, chunked prefill, radix cache) are
re-implemented here and then measured with ablations. Two components are new
relative to the blueprint: a C++ scheduling core and two-model speculative
decoding.

## Goals

- OpenAI-compatible API subset (`/v1/completions`, `/v1/chat/completions`, streaming SSE)
- Continuous batching over a paged KV cache
- Radix prefix cache with reference counting and LRU eviction
- Chunked prefill
- CPU-GPU overlap scheduling (one-step lag: step *t+1* is scheduled and launched before step *t* is read back)
- CUDA Graph capture for decode steps, bucketed by batch size
- Sampling: greedy, temperature, top-p, executed on the GPU without host synchronization
- C++ core (`minicore/`): block allocator, block tables, block-table packing into the attention kernel's paged metadata, and the radix tree, behind pybind11, validated against the Python reference implementation with the same test suite
- Two-model speculative decoding (draft: Qwen3-0.6B, target: Qwen3-8B): greedy verification with exact match to the target's own output. Rejection sampling for temperature > 0 is designed, not implemented

## Non-goals

- Tensor parallelism. Single-GPU is the premise: dropping TP complexity is what buys room for scheduling depth.
- Quantization, multi-model or multi-tenant serving, production-grade fault tolerance.
- Custom attention kernels. FlashInfer is used for paged attention, the same backend as the blueprint, so comparisons stay fair.
- Volta (sm_70). No BF16 and no FlashInfer / FlashAttention-2 support; porting would change both the dtype and the attention backend, so the comparison would no longer be of the same system.
- Full EAGLE. Public EAGLE-3 draft heads exist for Qwen3-8B, but wiring feature-level drafting and tree verification is close to a second model runner. Two-model drafting is the deliverable. A public EAGLE-3 head was measured inside sglang instead, on the same token ids: in a chain shape it emits 1.8–2.2 tokens per round against 3.1–3.7 for the 0.6B draft (`results/l40s/m5_6_*`); tree-shaped verification was not measured.

## Correctness anchor

Greedy output must match HF `transformers` token for token (same BF16 weights, same seed). Every feature that touches the forward path or the cache (batching, paged KV, radix cache, chunked prefill, CUDA Graphs, overlap, the C++ core) is required to leave greedy output unchanged, both for a single request and under a mixed concurrent load. The anchor is re-run on each platform the engine runs on.

Two levels of strictness apply. The plain-PyTorch reference model mirrors the transformers op order, so its prefill logits must be bitwise equal to HF. Paths that change GEMM shapes or kernels (batching, FlashInfer attention, fused norms) cannot be bitwise equal in BF16: even incremental decoding versus a full forward pass of the same sequence differs by up to 0.34 in logits, enough to flip argmax where the top two logits are one BF16 ulp apart. For those paths a sequence may diverge from the reference only at a position where the reference top-1/top-2 logit gap is at most ε; comparison of that sequence stops there. Divergence at a larger gap is a bug. Reports state ε and the divergence rate. Because that rule says nothing about tokens after the first divergence, every token a batched path produces is also checked teacher-forced: running the reference model on the path's own output, each chosen token's logit must be within ε of the reference maximum. With batching alone, ε = 0.5 (measured on 64 sequences of 128 tokens: largest gap at a divergence 0.25, most divergences at exact BF16 ties). In mutation tests, a decode-position off-by-one passed the first-divergence rule on every sequence and failed the teacher-forced check. With FlashInfer paged attention (16-token pages) ε stays 0.5: a single request is no longer bitwise equal to the reference, divergences occur at reference gaps of at most 0.125, and teacher-forced margins stay within 0.25. One bug class is nearly invisible at the token level: shifting every decode position by one looks to a RoPE model like an extra gap between prompt and output, so positions fed to the model are also checked exactly.

## Blueprint

Pinned at [`sgl-project/mini-sglang@9a91cfa`](https://github.com/sgl-project/mini-sglang/tree/9a91cfafe754aa85daee49998176275667eb58f2) (2026-05-17). All comparisons and module-by-module notes refer to this commit.

Where this engine deliberately differs:

| Area | mini-sglang | mini-serve | Why |
|---|---|---|---|
| Process model | API server, tokenizer, detokenizer and per-rank scheduler processes over ZMQ | One process: asyncio server, engine thread, tokenizer thread pool | No tensor parallelism, so multiple processes only add IPC |
| KV page size | 1 (its FlashInfer path asserts `page_size == 1`) | 16 by default, configurable | Smaller page tables and radix trees; requires real paged indices for FlashInfer |
| Admission | Reserves `prompt + max_tokens` KV slots up front; no preemption | Admission against a KV budget with preemption and pluggable policies (FCFS, shortest-first, cache-aware) | Lets 256 concurrent requests share a small pool, and makes scheduling policy an ablation axis |
| KV pool sizing | 90% of free memory minus weights | Peak activation profiled, plus an explicit `--kv-pool-tokens` override | Pool size is an experiment variable |
| Allocator / radix tree | Python, GPU-tensor free list, full-tree scan on each eviction | Python reference first, then a C++ core with the same tests; the C++ tree keeps evictable leaves in an ordered index, so an eviction no longer walks the tree | Data-structure hot paths moved to C++; on a 19,172-node tree one eviction goes from 5,553 µs (Python walk) to 804 µs (C++ walk) to 1.0 µs (index) |
| Paged-attention metadata | A token-level page table tensor on the GPU, flattened per step | Block tables on the host, packed per step into `indptr / indices / last_page_len` in resident pinned buffers, one C++ call per batch | Follows from 16-token blocks kept on the host; the packing was half of the Python host path |
| Speculative decoding | None | Two-model draft and verify: a separate draft KV pool sized like the target's, verification captured in CUDA Graphs bucketed by batch, the draft's prefill batched; the speculative path runs without overlap and without the prefix cache | Overlap needs the next batch before the current tokens are read back, and how many tokens a round accepts is known only after that readback; the prefix cache would let the target's block count drift from the draft's, which the equal-size draft pool relies on |
| Prefix cache | Radix tree at token (page size 1) granularity; node reference counts are the only record of sharing; eviction collects evictable leaves by walking the whole tree | Radix tree over 16-token blocks; the tree holds one allocator reference per cached block, node locks track running users; preempted requests leave their full blocks in the tree | Block granularity keeps the tree small; per-block reference counts let the allocator itself guarantee that eviction never frees a block in use; recomputation after preemption mostly hits the cache |
| Chunked prefill | Prefills are cut into chunks by a token budget, but prefill-only batches still run ahead of decode, so a long prompt's chunks run back to back while decoding requests wait | Decode first: every decoding request gets its token in every step and prefill chunks fill the rest of the step's token budget (mixed batches) | Bounds every step, so decoding requests are never stalled for a whole long prefill; chunks also fill GPU time that decode steps leave idle |
| Sampling | FlashInfer sampling kernels; random numbers drawn by row position in the batch; greedy rows in a mixed batch approximated by temperature 1e-6 | Gumbel-max with noise hashed from (request seed, token position, vocabulary index); greedy rows always take `argmax` | A request samples the same tokens wherever it sits in a batch and after preemption; greedy output never depends on its batch neighbours |
| Cancellation | The streaming loop checks `is_disconnected()` before sending each chunk; non-streaming requests are not cancelled | A per-request task waits for the client's `http.disconnect` and aborts immediately, for streaming and non-streaming requests alike | A request still queued (nothing sent yet) is cancelled at once; its KV blocks are returned whether it was waiting, decoding or requeued after preemption |
| Incremental detokenization | Holds text back until a word boundary (or a CJK character) as well as until characters are complete | Holds text back only while it ends in an incomplete character | Delaying text to word boundaries moves inter-token latency to spaces |
| API surface | `/generate`, `/v1/chat/completions`, `/v1/models`; stop strings and penalties accepted but ignored; `usage` reported as zeros | `/v1/completions`, `/v1/chat/completions`, `/v1/models`; unsupported parameters rejected with HTTP 400; real token counts in `usage` | A request is either served as asked or refused |
| Reference model | Fused FlashInfer ops from the start | Bitwise-HF reference path first; fused ops compared against it | Correctness anchor above |

CUDA Graph batch-size buckets differ by default between mini-sglang (up to 160), sglang 0.5.10 (up to 32) and this engine; comparisons set them explicitly and record them in the fairness checklist.

## Architecture

**Single process.** mini-sglang splits API server, tokenizer, detokenizer and one scheduler per GPU rank into separate processes over ZMQ, which exists to serve tensor-parallel ranks. Without TP that structure leaves only IPC overhead, so this engine collapses to one process: a uvicorn/FastAPI event loop for HTTP and SSE, an engine thread running the `step()` loop (schedule → forward → sample → postprocess), and a tokenizer thread pool. The known cost is GIL contention between HTTP, tokenization and Python scheduling. The tokenizer interface is replaceable by a subprocess if profiling shows it starving the engine loop; this is expected to matter most on hosts with weak single-thread CPUs.

```
miniserve/
├── server/        FastAPI, OpenAI protocol adapter, SSE
├── engine/        scheduler.py, model_runner.py, sampler.py
├── cache/         Python reference BlockAllocator / RadixTree
├── minicore/      C++ core (pybind11) + gtest
├── spec/          speculative decoding
├── bench/         benchmark wrappers, ablation scripts, fairness checklist, environment sidecar
└── tests/         unit / consistency / stress
```

Core types: `Request` (prompt ids, sampling params, state machine WAITING → PREFILL → DECODE → FINISHED/ABORTED, plus DECODE → WAITING on preemption), `Batch` (requests in this step plus block tables and positions), `BlockTable` (request → physical blocks).

## Key decisions

- **KV block size** defaults to 16 (configurable to 1). The radix tree is built at block granularity; a little prefix hit rate is traded for bounded metadata.
- **KV pool size is a first-class experiment variable.** The pool is auto-sized at startup (after loading weights, run one prefill of `--max-prefill-tokens` tokens to measure peak activations, give 90% of the remaining free memory to KV, derive block count from the model config), but `--kv-pool-tokens N` sets it exactly. A size that does not fit in memory is an error rather than silently clipped, since the value is reported as an experiment coordinate. On a large GPU the pool is big enough that scheduling policies converge; sweeping the pool size turns that hardware limit into a controlled axis.
- **Admission against a block budget, preemption by recomputation.** A waiting request of `L` tokens is admitted only if the pool can hold its prefill plus one decode token, after setting aside the blocks every running request needs for its next token; admission stops at the first request that does not fit. So right after any admission the next decode step fits. When a later decode step does not, the most recently admitted requests are preempted until it does: their blocks are freed, their generated tokens kept, and they return to the front of the waiting queue. On readmission the prefill runs prompt + generated tokens, whose last-position logits are exactly those of the interrupted decode step. This cannot deadlock: requests that could not fit in the whole pool are rejected on submission, and the oldest running request is never preempted, so it always makes progress. mini-sglang instead reserves `prompt + max_tokens` for every request and never preempts, which wastes the reservation of every request that stops early.
- **Prefix cache at block granularity.** A radix tree maps token prefixes, in whole 16-token blocks, to the KV blocks that hold them. Admission looks up the longest cached prefix of a request (leaving at least its last token to compute, for its logits), starts the request's block table with those blocks and charges the KV budget and the prefill token budget only for the uncached part. After a prefill the request's full blocks are inserted, so later requests with the same prefix hit while it is still decoding; when a request finishes, is cancelled or is preempted, its full blocks stay in the tree. Blocks held only by the tree count as available and are evicted least recently used first when the free pool is short. Sharing has a second effect beyond skipped prefill: in decode, the attention kernel reads a shared block from DRAM once and serves the other sequences' reads from L2, so a larger batch of requests with a common prefix costs little more memory traffic than a small one. With a prefix cache, a request's computation depends on what is cached, so at BF16 near-ties its greedy output can differ from an uncached run; the correctness anchor's tolerance covers it, and exact comparisons start from an empty cache.
- **Chunked prefill batched with decodes.** With a per-step token budget (`--chunked-prefill-size`, default 2048; 0 restores prefill-only steps), each step first gives every decoding request its token, then spends the rest of the budget on prefill chunks: requests already part-way through their prefill first, then new admissions in arrival order. Admission still reserves blocks for the whole prefill plus one token; chunks allocate them step by step, and a request can be preempted between chunks (its computed full blocks stay in the prefix cache). A step with both decode rows and prefill chunks runs through the prefill attention kernel, where a decode row is a causal row of length one. Two measured consequences shape how the budget should be chosen. The tail of the inter-token latency depends on how many decode steps a prefill stall is spread over, not only on how long the longest stall is: with a few long prompts in a stream of short requests, 2048-token chunks cut the longest gap but double the 99th percentile, while 512-token chunks lower both. And chunking can raise throughput: a mixed step costs much less than a prefill-only step plus a decode step. Part of that was eager decode steps leaving the GPU idle between kernel submissions, which CUDA Graphs remove (with graphs, 512-token chunks raise burst throughput by 21% instead of 27%); the rest remains.
- **Sampling stays on the device, and is reproducible per request.** Greedy, temperature and top-p sampling run without host synchronization; the sampled tokens are copied back once per step with a non-blocking copy and an event, the only point where the host waits for the device after sampling. Sampled rows use the Gumbel-max trick (`argmax(logits / T + g)`, with tokens outside the nucleus masked out first); the noise `g` is not drawn from a stateful generator but hashed from the request's seed, the position of the token being sampled, and the vocabulary index. Batch composition, a request's row in the batch, and preemption with recomputation therefore do not change which noise a request sees. The price is a sort for top-p and `[batch, vocab]` temporaries, which the KV pool sizing accounts for.
- **The engine thread owns the engine; the event loop only sends commands.** `Engine` is not thread-safe and `step()` blocks for the duration of a forward pass, so it runs on a dedicated thread. The HTTP side sends add / abort / call commands through a FIFO queue that the engine thread drains between steps (and blocks on when idle); since the queue is FIFO, an abort always reaches the engine after the add it refers to. After each step the engine thread hands the new tokens of the whole batch to the event loop in one `call_soon_threadsafe`, and one coroutine detokenizes them with one tokenizer call per batch. The tokenizer sits behind an interface whose per-request decoding state lives inside the backend, so a subprocess backend can replace the thread pool without touching the rest. OpenAI defaults apply at the API boundary (`temperature` 1.0), not in the engine (whose default is greedy).
- **Scheduling policy is a plugin** (`SchedulePolicy`): the order in which waiting requests are admitted, and which running request is preempted. FCFS (arrival order; the newest admitted is preempted), shortest-job-first (least remaining prefill plus possible output first; the largest is preempted) and cache-aware (longest cached prefix first, from a read-only radix lookup that neither splits nodes nor touches access times, so ranking does not change eviction). Admission tries requests in the policy's order and stops at the first that does not fit; the earliest admitted running request is never a preemption candidate, which keeps the progress guarantee under any policy. Order only matters while requests queue for KV: on the development GPU, with 128 requests arriving at once in 16 prefix-sharing groups, cache-aware raised throughput by 25–27% and shortest-job-first cut mean latency by 42–49% (short requests by 74–80%) in 6k- and 8k-token pools, while in a 16k-token pool all three were within 5% on throughput and latency. With a single burst, shortest-job-first did not hurt long requests (their p99 changed by −4% to +2%): a steady stream of short arrivals, which can starve them, was not measured. Policies stay in Python; data structures and hot paths move to C++.
- **Overlap scheduling** follows the one-step-lag scheme: each step launches batch *t+1* before it reads back batch *t*, so the CPU schedules and prepares *t+1* while the GPU runs *t*. A request that sampled a token in *t* gets a placeholder output token; its input in *t+1* is copied from *t*'s sampled tokens on the device, and positions, block tables and sampling counters already count the placeholder. A request that has sampled its last allowed token is not scheduled again and, under KV pressure, is preempted first, at no cost; a request that turns out to have sampled a stop token in *t* already has a row in *t+1*, whose token is discarded. Releasing the KV of a request that ended in *t* while *t+1* still uses it is safe on one stream: the blocks can only be handed out when *t+2* is formed, and *t+2* runs after *t+1*. For the CPU to actually run ahead, nothing on the launch path may wait for the device: every host-to-device copy comes from pinned memory without blocking (a copy from pageable memory first waits for the whole stream), including the attention planner's metadata. On the development GPU, after CUDA Graphs, the decode step has little CPU time left to hide, as a graph replay starts while the rest of the step is still being prepared; overlap raised throughput by 2.9% for 64 requests at once, where the Nsight Systems timeline shows GPU idle time over the run falling from 344 ms (95.6% busy) to 155 ms (97.9% busy), and by 1.6% for 4 requests. Without CUDA Graphs it gave 7.2%: an eager decode step is bound by the CPU issuing its kernels one by one, and overlap cannot make a step shorter than its CPU time. It costs time to first token: a sampled token is read back one step later, after the next step is launched, which adds about one decode step (+4% at 4 requests, where TTFT is a 230 ms prefill; +26% for short requests in a 4 req/s stream, where TTFT is 31 ms). In that stream, inter-token latency improved slightly (p50 −2%, p99 −7%) and throughput, set by the arrival rate, did not change. `--disable-overlap` turns it off.
- **CUDA Graphs** are captured for decode only, one graph per batch-size bucket (powers of two up to the running-batch limit, and the limit itself), with padding up to the bucket; padding rows write and read a spare KV block that the allocator never hands out, so they cannot touch a request's KV. Token ids, positions and KV slots go through one pinned staging buffer into the graphs' static inputs; FlashInfer's CUDA-graph decode wrappers take the paged-KV metadata in buffers fixed at capture, which `plan` overwrites every step. Sampling stays outside the graph. Graphs are captured after the KV pool is allocated, largest first into one shared memory pool. Measured effect on the development GPU: an eager decode step at small batch is bound by kernel submission, about 19.5 ms whatever the batch; replayed from a graph it takes 8–10 ms. With 64 requests at once (decode batches of about 20), the Nsight Systems timeline shows the same GPU work per decode step either way, about 19 ms, with the GPU busy 61% of an eager step and 96% of a graph step. When comparing against another engine, graph bucket configurations are aligned and recorded.
- **Environment is a build artifact.** The Dockerfile is the development environment; the same image is converted to an Apptainer SIF for cluster runs. Host compilers on shared clusters vary by node type, and this project depends on three layers of JIT (Triton, FlashInfer, and the baseline's sgl-kernel), so the toolchain travels with the project. JIT caches are redirected out of `$HOME` and pre-warmed. Every cluster job starts with a preflight assertion.
- **The C++ core crosses the language boundary once per unit of work, not once per object.** The first version moved the allocator and block tables to C++ and left their consumer, the per-step packing of block tables into paged-attention metadata, in Python; every step then turned 248 C++ vectors into Python lists, and the host path got 4.8% slower. Moving the packing too (one call writes a whole batch into pinned buffers) made it 40% shorter than the Python reference (0.920 vs 1.541 ms at batch 248). The same rule shaped the prefix tree's interface: a batched `prefix_lens` query for cache-aware admission removed 60% of its cost before any C++ was involved. The Python reference stays the default backend: with CUDA Graphs and overlap the saved host time is off the critical path on both GPUs measured (4,019.2 vs 4,019.2 tok/s on the L40S).
- **Speculative decoding verifies greedily and gives up overlap.** The draft proposes γ tokens one step at a time; the target scores all of them plus one in a single pass, and the longest prefix whose tokens equal the target's argmax is kept, then the rejected tail is rewound out of both block tables. Output is therefore the target's own greedy output, held to the same tolerance as every other path. Two costs are structural: the round must read back before the next one is formed, so there is no overlap; and acceptance is not a property of the draft alone — at exact BF16 ties the decode and prefill kernels choose differently, so even the target drafting for itself accepts 0.944–0.970 (development GPU), and every acceptance figure is reported beside that self-draft ceiling. Which γ is best depends on the round's fixed cost: once verification ran from graphs the best γ moved from 4 to 2 on the development GPU. On the L40S the 0.6B draft is not 7.5% of the 8B target, as the parameter ratio suggests, but 44% of a round: at batch 8 its step is bound by kernel latency (5.2 ms against a 1.83 ms bandwidth floor).
- **No `-march=native`, no `-arch=native`.** The C++ core and any nvcc invocation pin an explicit CPU baseline and `sm_89`, because a `.so` built on a node with AVX-512 crashes with SIGILL on a node without it.

## Platforms

| Platform | Role |
|---|---|
| RTX 4060 Laptop (Ada, 8 GB) | Development, unit tests, correctness, small-scale profiling. Secondary benchmark numbers, reported with the 8 GB caveat. |
| L40S 48 GB (Ada) | Primary benchmark: 256 concurrent sequences fit in the KV pool, ablations, comparison against mini-sglang and sglang. |
| H100 80 GB (Hopper) | Second data point for the CPU:GPU pairing (overlap across platforms). The only one of the three where hardware counters are readable; not needed so far. |

The port is a container: the development image is converted to an Apptainer image and copied to the cluster, so both run the same bytes; the code is a checkout of this repository, and every JIT and model cache lives in project storage, outside the home directory. A job's first step asserts all of that (`psc/preflight.sh`), and the image is started with the target GPU's architecture in `TORCH_CUDA_ARCH_LIST` / `FLASHINFER_CUDA_ARCH_LIST`, since attention and Triton kernels are compiled at run time. Correctness across devices is checked per device: the engine against that device's own reference path, which is where the tolerance policy applies. The reference path is not bitwise identical across GPUs (on three of six anchor prompts the 4060 and the L40S pick different tokens at exact BF16 ties, from token 4, 5 and 17), so requiring identical output across devices would report normal numerics as a bug.

L40S and the 4060 share the same SM architecture constants, so code written locally runs on the cluster without architectural adaptation. Their CPU:GPU balance is very different, which is exactly what makes the overlap scheduling ablation informative across platforms.

The CPU that comes with a GPU matters as much as the GPU. The development host is a Ryzen 9 7945HX; the L40S node an Intel Xeon 6740E (efficiency cores, no AVX-512); the H100 node an Intel Xeon Platinum 8470. Measured with one harness and a pinned pool, overlap's gain is roughly the host time it hides per step divided by the step time; the hidden host time at a batch of 32 is 0.18, 0.25 and 0.40 ms on the three hosts, in the order of their per-core speed. So the H100 gains less than the L40S at small batches (3.2% vs 5.4% at a cap of 8), where a 0.6B step is held up by 3–4 ms that is not memory traffic and the H100 is only 1.17× faster, and more at large ones (10.9% vs 6.8% at 128). An overlap figure is quoted with its GPU, its CPU and its harness (`results/*/m5_7_overlap.csv`).

## Measurement

- Benchmark harness: genai-bench. Reported: TTFT p50/p95, TPOT / inter-token latency p50/p99, output throughput. Both a low-concurrency and a high-concurrency operating point are reported.
- Every number is given three ways: absolute, relative to the baseline, and as a fraction of the hardware ceiling.
- Warm-up is by time and clock state, not by request count: at least 30 s, and until the last window of SM clock samples agrees with the one before within 2% — or, for loads whose short windows never agree (an 8B model's prefills hit the power cap and its decodes do not), until a whole warm-up run's mean clock agrees with the previous run's. Both engines under comparison use the same rule; clocks cannot be pinned on any of the three devices, so the trace goes into the sidecar instead.
- Fairness checklist for any comparison: pinned baseline commit and container image digest, dtype, attention backend and version, KV pool size, `max_num_batched_tokens`, CUDA Graph configuration, sampling parameters, CPU model, warmup window, ABBA alternation within the same job, median of ≥3 rounds.
- Clock, memory clock, temperature, power draw, power limit, GPU utilization and memory in use are recorded before and after each run in a sidecar file; the harness refuses to write results without it.
- Chunked prefill is evaluated on decode inter-token latency p99, not on peak memory, because with a pre-allocated KV pool peak memory does not change.
- Two harnesses, two questions. The engine-level harness (`bench/offline.py`) feeds token ids straight into the engine and alternates the compared settings in one process; it answers what a feature does to the engine. genai-bench over HTTP answers what a user sees, and includes the server's own host work: on the same L40S, overlap gains +5.2% in the first and +14.7% in the second at the same concurrency.
- Denominators are measured on each device (`bench/roofline.py`: copy and read-only bandwidth, BF16 GEMM rate), never taken from a specification. Published fractions of peak use copy bandwidth; a decode step's floor is `(weights + batch × context × KV bytes per token) ÷ bandwidth`, and what remains above it is reported as what it is: everything the bandwidth model does not explain, not host time.
- A profiler changes what it measures. Under Nsight Systems the overlap-off arm's decode step grows by 20% while the overlap-on arm's barely moves, because tracing cost lands on the host path and overlap hides it; read from a timeline, overlap's gain would be +24% instead of +5.2%. Magnitudes come from unprofiled runs; timelines are for shape.
- Comparing against another engine with repeated runs of one workload rewards the side that keeps more of the previous run in its prefix cache; the blueprint comparison empties its cache before every timed run.
- A change is merged only after a two-arm benchmark on the development GPU stays within 5% of a recorded baseline (`make gate`). Drift across sessions has reached 3–6% on unchanged code, so far a failure has been re-checked by hand against the baseline commit in the same session before it counts; building that into the check is the first item of open work below.
- Negative results are reported as measured.

## Roadmap

| Stage | Deliverable | Done when |
|---|---|---|
| M0 | Skeleton: environment, weight loading, single-request greedy generation | Token-exact match with HF transformers |
| M1 | Continuous batching, paged KV, FlashInfer attention, API | 64 mixed concurrent requests, no OOM, output unchanged |
| M2 | Radix cache, chunked prefill | Hit rate > 0, output unchanged |
| M3 | CUDA Graphs, overlap scheduling, scheduling policies | Ablation switches work; CPU gaps visibly narrow in the nsys timeline |
| M3.5 | Cluster port: container, preflight, end-to-end service on L40S | Greedy output on each device within tolerance of that device's reference path |
| M4 | Benchmarks and three ablations on L40S; local regression gate | Every plotted line traces to a row in `results/` |
| M5 | C++ core; two-model speculative decoding | C++ backend passes the same tests as the Python reference; spec decoding reported with acceptance rate and large-batch regression |

Status: all stages complete (tag `v1.0`); the numbers behind each are in `optimization-log.md`.

- **Implemented and ablated**: everything in the Goals list except the two items below, each with a switch that turns it off (`--disable-radix`, `--chunked-prefill-size 0`, `--disable-cuda-graph`, `--disable-overlap`, `--schedule-policy`, `--kv-pool-tokens`, `--block-backend`) and a measured effect on at least one GPU. Primary numbers on the L40S, head-to-head against sglang 0.5.10 in the same job and against the blueprint on the development GPU.
- **Implemented, not the default**: the C++ core (`--block-backend cpp`), for the reason in Key decisions.
- **Designed, not implemented**: rejection sampling for speculative decoding at temperature > 0; speculative decoding behind the HTTP server (it runs through the engine-level harness).

Open work, in the order it is planned (local work first, then two cluster jobs submitted together so that they queue once):

1. **Regression check.** Its baseline drifts across sessions by more than half the 5% threshold on unchanged code; compare against the baseline commit re-run in the same session, and record the host state that might explain the drift.
2. **One warm-up rule.** The clock-settling rule that ends warm-up is implemented three times in the benchmark tools, and one copy falling behind cost a whole benchmark job; one implementation should serve all of them.
3. **Cache-aware ordering in C++.** With the C++ tree, the remaining cost of cache-aware admission is assembling and sorting the queue on the Python side (0.116 of 0.198 ms per step on the development host, 1.17 ms on the L40S node); compute the ordering key and the order in one call.
